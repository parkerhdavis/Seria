## Before You Start

### Check Existing Work

Before starting on a contribution:

1. **Check existing issues:** [GitLab Issues](https://gitlab.com/parkerhdavis/Seria/-/issues)
   - See if someone is already working on what you want to do
   - Look for issues labeled `good first issue` or `help wanted`

2. **Discuss large changes:** For major features or architectural changes:
   - Open an issue first to discuss the approach
   - Get feedback before investing significant time
   - Ensure the change aligns with project goals

3. **Read the development docs:**
   - [Developer Quick Start](05.01_DeveloperQuickStart.md) - Basic setup
   - [Development Guide](05.02_DevelopmentGuide.md) - Detailed development info
   - [Project Quirks](05.06_ProjectQuirks.md) - Non-standard patterns to be aware of

## Getting Set Up

### Fork and Clone

1. **Fork the repository** on GitLab
   - Click "Fork" button on the [Seria repository](https://gitlab.com/parkerhdavis/Seria)

2. **Clone your fork:**
   ```bash
   git clone https://gitlab.com/YOUR_USERNAME/Seria.git
   cd Seria
   ```

3. **Add upstream remote:**
   ```bash
   git remote add upstream https://gitlab.com/parkerhdavis/Seria.git
   ```

### Set Up Development Environment

Run the setup script:
```bash
make setup
```

Verify everything works:
```bash
make dev
```

The Seria window should open with hot-reload enabled.

## Contribution Workflow

### 1. Create a Feature Branch

```bash
# Update your main branch
git checkout main
git pull upstream main

# Create a new branch
git checkout -b feature/my-feature-name
```

**Branch naming conventions:**
- `feature/description` - New features
- `fix/description` - Bug fixes
- `docs/description` - Documentation changes
- `refactor/description` - Code refactoring

### 2. Make Your Changes

Follow the [coding standards](#coding-standards) below.

**Key points:**
- Write clear, commented code
- Add tests for new functionality
- Update documentation as needed
- Follow existing code style

### 3. Test Your Changes

Before committing:

```bash
# Run linting
make lint

# Run tests
make test

# Build to verify no compilation errors
make build
```

### 4. Commit Your Changes

```bash
git add .
git commit -m "Clear description of what changed"
```

See [commit guidelines](#commit-guidelines) below for formatting.

### 5. Push to Your Fork

```bash
git push origin feature/my-feature-name
```

### 6. Create a Merge Request

1. Go to your fork on GitLab
2. Click "Create merge request"
3. Fill out the merge request template:
   - **Title:** Brief summary of changes
   - **Description:** Detailed explanation of what and why
   - **Related issues:** Link to any related issue numbers
   - **Testing:** Describe how you tested the changes

### 7. Respond to Feedback

- Address code review comments
- Make requested changes
- Push updates to the same branch (will update the MR automatically)

## Coding Standards

### General

- **4-space indents** (not 2-space) - See [Project Quirks](05.06_ProjectQuirks.md)
- **Double quotes** for strings
- **Comprehensive comments** on all files, classes, and complex logic
- Follow existing code style in each file

### TypeScript/React

- Use **functional components** with hooks (no class components)
- Use **TypeScript interfaces** for all props and state
- **Name components** in PascalCase: `CSVGrid.tsx`
- **Name utilities** in camelCase: `csvParser.ts`
- Add **JSDoc comments** to all exported functions

**Example:**
```typescript
/**
 * Parses a CSV string into a 2D array.
 *
 * @param csvText - Raw CSV text content
 * @param hasHeader - Whether the first row is a header
 * @returns Parsed CSV data as 2D string array
 */
export function parseCSV(csvText: string, hasHeader: boolean): string[][] {
    // Implementation
}
```

### Styling

- Use **DaisyUI components** wherever possible
- Use **semantic utilities**: `bg-base-100`, `text-primary`, etc.
- **Never hard-code colors** - use CSS variables or DaisyUI classes
- Support **both light and dark themes**

### Rust

- Keep Rust code **minimal** - only for file I/O
- Use `Result<T, String>` for all Tauri commands
- Add **doc comments** to all public functions
- Follow Rust standard formatting (`rustfmt`)

**Example:**
```rust
/// Opens a CSV file and returns its contents as a string.
///
/// # Arguments
/// * `path` - Absolute path to the CSV file
///
/// # Returns
/// * `Ok(String)` - File contents
/// * `Err(String)` - Error message
#[tauri::command]
fn open_csv_file(path: String) -> Result<String, String> {
    // Implementation
}
```

### ESLint Disable Comments

When using `eslint-disable-next-line`, **always document:**
1. What error is being disabled
2. Why it's being disabled
3. What alternatives exist

**Example:**
```typescript
// Disabled: Missing handleStartEdit dependency
// Reason: handleStartEdit is stable, adding would cause infinite loop
// Alternative: Wrap in useCallback, then add to dependencies
// eslint-disable-next-line react-hooks/exhaustive-deps
```

## Commit Guidelines

### Commit Message Format

Use clear, descriptive commit messages:

```
Add feature: brief description (50 chars or less)

- More detailed explanation if needed
- Use bullet points for multiple changes
- Reference issue numbers: Fixes #123
```

**Good examples:**
```
Add bidirectional editing to Print view

- Implement click-to-edit in Print preview
- Update CSV store when Print changes
- Add tests for bidirectional sync

Fixes #45
```

```
Fix column width persistence bug

Column widths were not saving when auto-fit was enabled.
Changed save trigger to fire after auto-fit completes.

Fixes #67
```

### Commit Message Guidelines

**DO:**
- Use present tense: "Add feature" not "Added feature"
- Be specific: "Fix CSV parsing for quotes" not "Fix bug"
- Reference issues: "Fixes #123" or "Relates to #456"
- Keep first line under 50 characters
- Add details in body if needed

**DON'T:**
- Use vague messages: "Fix stuff" or "Update code"
- Include multiple unrelated changes in one commit
- Forget to test before committing

## Code Review Process

All contributions go through code review:

### Requirements

- [ ] Code follows project coding standards
- [ ] All tests pass (`make test` succeeds)
- [ ] Linting passes (`make lint` succeeds)
- [ ] New features include tests
- [ ] Documentation is updated
- [ ] Commit messages are clear and descriptive

### Review Timeline

- Small changes (bug fixes, docs): 1-3 days
- Medium changes (new features): 3-7 days
- Large changes (architecture): 1-2 weeks

### Addressing Feedback

When reviewers request changes:

1. **Read feedback carefully** - Understand what's being requested
2. **Ask questions** if anything is unclear
3. **Make changes** in your feature branch
4. **Push updates** - They'll appear in the merge request automatically
5. **Respond to comments** - Let reviewers know when you've addressed their feedback

## Types of Contributions

### Bug Fixes

1. **Find or create an issue** describing the bug
2. **Write a test** that reproduces the bug (if possible)
3. **Fix the bug** and verify the test passes
4. **Submit merge request** with issue reference

### New Features

1. **Open an issue** to discuss the feature
2. **Get feedback** on approach and design
3. **Implement the feature** following coding standards
4. **Add tests** for the new functionality
5. **Update documentation** (user guide, developer docs)
6. **Submit merge request**

### Documentation

Documentation contributions are highly valued!

**User documentation** (`wiki/`):
- User guides
- Feature explanations
- FAQ entries
- Screenshots and examples

**Developer documentation** (`wiki/05_Development/`):
- Setup guides
- Architecture explanations
- API documentation
- Troubleshooting guides

**Process:**
1. Edit or create documentation files
2. Test any code examples
3. Check formatting and links
4. Submit merge request

### Testing

Help improve test coverage:

1. **Identify untested code** - Look for features without tests
2. **Write test cases** - Both unit and integration tests
3. **Document test procedures** - Manual testing guides
4. **Submit merge request**

### Design and UX

Contributions to UI/UX design:

1. **Open an issue** with mockups or proposals
2. **Discuss with maintainers** - Get feedback on approach
3. **Implement changes** following DaisyUI patterns
4. **Test on multiple screen sizes**
5. **Submit merge request** with screenshots

## Getting Help

**If you get stuck:**

1. **Check existing documentation:**
   - [Development Guide](05.02_DevelopmentGuide.md)
   - [Building and Distribution](05.03_BuildingAndDistribution.md)
   - [Project Quirks](05.06_ProjectQuirks.md)

2. **Search existing issues:**
   - Someone may have had the same problem
   - Check closed issues too

3. **Ask for help:**
   - Comment on the related issue
   - Open a new issue with "Question:" prefix
   - Be specific about what you've tried

4. **Review existing code:**
   - Look at similar features for examples
   - Check test files for usage patterns
