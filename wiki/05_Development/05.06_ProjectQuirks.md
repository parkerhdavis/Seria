## Cargo Target Directory Location

### The Quirk

Unlike most Rust projects where build artifacts live in `backend/target/`, Seria places all Rust build output in the **top-level `target/` directory**.

**Standard Rust project:**
```
backend/
├── src/
├── Cargo.toml
└── target/           # Build artifacts here
```

**Seria project:**
```
Seria/
├── backend/
│   ├── src/
│   └── Cargo.toml
└── target/           # Build artifacts here (at project root)
```

### Why This Exists

This configuration:
1. Keeps all build artifacts in one place
2. Prevents accidentally committing build outputs (single `.gitignore` entry)
3. Makes it easier to clean all artifacts with one command
4. Mirrors how frontend build outputs are structured

### How It Works

This is configured in `backend/.cargo/config.toml`:

```toml
[build]
target-dir = "../target"
```

This tells Cargo to use the parent directory's `target/` folder instead of creating one inside `backend/`.

### What This Means for You

**Build output locations:**
```
target/
├── debug/                      # Development builds (unoptimized)
│   ├── Seria                # Executable
│   ├── deps/                  # Compiled dependencies
│   └── incremental/           # Incremental compilation cache
│
├── release/                    # Production builds (optimized)
│   ├── Seria                # Optimized executable
│   ├── bundle/                # Installers (.deb, .rpm, .AppImage, etc.)
│   └── deps/                  # Compiled dependencies
│
└── x86_64-pc-windows-msvc/    # Windows cross-compilation builds
    └── release/
        └── bundle/            # Windows installers (.exe, .msi)
```

**Cleaning build artifacts:**
```bash
# Remove all build artifacts (frees ~1.5-2 GB)
cargo clean

# From project root (not backend/)
rm -rf target/
```

**Impact on documentation:**
- Build guides reference `target/release/bundle/` not `backend/target/release/bundle/`
- CI/CD scripts must look in top-level `target/`
- Cross-platform builds organize by target triple under top-level `target/`

### Disk Space Usage

Typical space consumption:

- **Initial debug build:** ~500 MB - 1 GB (includes all dependencies)
- **Initial release build:** ~500 MB - 1 GB
- **Both debug + release:** ~1.5 - 2 GB
- **With incremental cache:** Add ~200-500 MB

**Cleanup tips:**
```bash
# Remove all build artifacts
cargo clean

# Remove only debug artifacts (frees ~500 MB - 1 GB)
rm -rf target/debug

# Remove only release artifacts (frees ~500 MB - 1 GB)
rm -rf target/release
```

### Troubleshooting

**Issue: "Cannot find target directory"**

If you're running `cargo` commands directly:
```bash
# Run from backend/ directory
cd backend && cargo build

# OR run from project root
cargo build --manifest-path backend/Cargo.toml
```

**Issue: Build cache corruption**

If you see strange compilation errors:
```bash
cargo clean
cargo build
```

## Version Management

### The Quirk

Seria uses **a single source of truth for version numbers** instead of maintaining versions in multiple files manually.

**Standard approach (manual sync):**
- Update `frontend/package.json` version
- Update `backend/tauri.conf.json` version
- Hope you remembered both and they match

**Seria approach (single source of truth):**
- Update `VITE_APP_VERSION` in `.env`
- Build script automatically syncs to `backend/tauri.conf.json`
- Never manually edit version in Tauri config

### Why This Exists

This prevents:
- Version mismatches between frontend and backend
- Forgetting to update version in one place
- Release mistakes due to incorrect version numbers

### How It Works

1. **`.env` file** contains the source of truth:
   ```bash
   VITE_APP_VERSION=0.2.0
   ```

2. **`scripts/sync-version.sh`** runs during build:
   - Reads `VITE_APP_VERSION` from `.env`
   - Updates `backend/tauri.conf.json` version field
   - This happens automatically during `make build`

3. **`frontend/package.json`** can be updated independently (for npm purposes)

### What This Means for You

**To change the app version:**

1. Edit `.env`:
   ```bash
   VITE_APP_VERSION=0.3.0
   ```

2. Run build (version syncs automatically):
   ```bash
   make build
   ```

3. Version is now consistent across:
   - Frontend app metadata
   - Tauri config
   - All installers (.deb, .rpm, .msi, etc.)

**DON'T manually edit:**
- `backend/tauri.conf.json` version field (will be overwritten)

**DO edit:**
- `.env` `VITE_APP_VERSION` field (source of truth)

### Version Format

Follow [Semantic Versioning](https://semver.org/):
- `MAJOR.MINOR.PATCH`
- Example: `0.1.0` → `0.2.0` (new features) → `0.2.1` (bug fix)

## Directory Structure

### The Quirk

Seria has a two-tier documentation structure:

```
Seria/
├── wiki/              # Public-facing user documentation
│   ├── 01_Introduction/
│   ├── 02_Cell View/
│   ├── 05_Development/  # Public developer docs
│   └── 06_FAQ and Support/
│
└── wiki-internal/     # Internal developer documentation (git-ignored)
    ├── KICKOFF_PLAN.md
    ├── TASK_*.md
    └── (other internal notes)
```

**Standard approach:** All docs in one place (e.g., `docs/`)

**Seria approach:** Public docs in `wiki/`, internal docs in `wiki-internal/`

### Why This Exists

- `wiki/` syncs to GitHub for users
- `wiki-internal/` contains development notes, personal TODOs, sensitive information
- Keeps public documentation clean and user-focused

### What This Means for You

**When writing documentation:**
- User-facing guides → `wiki/`
- Technical implementation notes → `wiki-internal/`
- Development planning → `wiki-internal/`
- Contribution guides → `wiki/05_Development/`

## Coding Style Differences

### The Quirk

Seria uses **4-space indents** instead of the JavaScript/TypeScript community standard of 2-space indents.

**Standard JS/TS:**
```typescript
function example() {
  return {
    key: "value"
  };
}
```

**Seria style:**
```typescript
function example() {
    return {
        key: "value"
    };
}
```

### Why This Exists

- Consistency with Rust code (which uses 4-space indents)
- Improved readability for deeply nested structures
- Personal preference from project creator

### What This Means for You

- Configure your editor to use 4-space indents for this project
- ESLint/Prettier configurations enforce this
- Don't change existing indent style when contributing

**VSCode settings (workspace):**
```json
{
    "editor.tabSize": 4,
    "editor.insertSpaces": true
}
```

## Additional Quirks

### String Quotes

Seria prefers **double quotes** over single quotes:

```typescript
// Preferred
const message = "Hello, world";

// Avoid
const message = 'Hello, world';
```

### Documentation Style

Documentation avoids exclamation points for a more professional tone:

```markdown
<!-- Preferred -->
Seria automatically saves your changes after you finish editing cells.

<!-- Avoid -->
Seria automatically saves your changes after you finish editing cells!
```
